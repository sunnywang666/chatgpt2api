## 公司账号池与调用者的程序密钥

录入此池的上游账号统一作为公司资源，录入人不是账号的个人所有者。调用者自己管理的是访问公司池的程序 Key，不需要先导入、认领或拥有上游账号。账号管理权限与普通调用权限分开；应用不取得上游登录凭据，也不需要池管理员密钥。历史记录中的提交人、原账号引用和回执访问权限不随本次纠正迁移。

在本人已有访问权限的工作台「ChatGPT / Codex → 密钥与 CLI」中，为目标应用创建并命名 Key，选择它要使用的 Chat／Codex 端。完整 Key 仅在创建响应中返回，私密保存到目标应用的环境配置；列表只显示元数据，不能找回完整秘密。不要把真实 Key 放进“复制给 AI 配置”、聊天、日志或代码。

Key 的名称只需在同一使用者、同一角色的记录中区分；不同使用者可以都叫“工作流”，不会互相占用名称或默认编号。内部无归属的旧 Key 保留自己的名称范围；不迁移、不认领旧 Key。名称不是鉴权身份，查询、修改和撤销仍按原 Key ID 与归属校验。撤销保留记录、关闭后续鉴权，不删除旧任务或改动已受理任务；另一把同名 Key 不受影响。已撤销名称仍保留，不会通过同名创建隐式复活旧 Key。

账号额度响应中的 `remaining` 可能是最后一次成功读取的历史值。只有 `state=observed` 才表示通过现有五分钟新鲜度检查的有效观测；有值但已过期、调用后待刷新、缺失或异常时间时为 `stale`，读取失败为 `read_failed`，没有有效额度数值为 `unknown`。真实零不改成未知，未知不伪造为零。刷新取得新的有效观测后可重新显示 `observed`；这段只说明观测投影，不将它冒充额度恢复后自动调度已经验收。

### 公司账号录入与管理链路（候选，未部署）

公司录入的 Provider 内部路径为 `POST /api/workbench/ai/pool/accounts`；配套工作台 BFF 为 `POST /api/v1/content/ai-service/pool/accounts`。这两个是受保护的管理入口，不写进普通模型 Key 的调用示例。工作台继续核对老板／管理员身份、登录会话与同源请求，Provider 继续使用既有内部管理鉴权。

录入复用原身份核验、去重与凭据保存处理器，不创建第二个账号库。成功后从原账号记录生成公司视图，返回 `resource_scope=company`，`item.id`、`item.account_ref` 和 `item.authorization_ref` 为同一稳定公司引用。工作台校验三者一致；不能把旧个人行 ID 当成公司引用。公司列表、刷新、启停和改名继续使用已有 `/pool/accounts` 系列接口，不按最初录入人筛选资源。

导入 Chat 授权使用现有受验证导入；Codex 使用完整授权材料。显式指定 Codex 授权目标时走已有的身份核验附加入口，不让按凭据自动匹配的导入器无声改动其他账号。导入后无法确认原公司记录时返回 `COMPANY_ACCOUNT_READBACK_REQUIRED`，结果保持未知，不自动再次导入或重做授权交换。

管理桥接成功响应保持 `private, no-store`。重复启用不意味着新增额度；现有公司启停处理器保留最后的额度证据，重新启用仍需成功刷新。刷新 HTTP 200 不等于每个端都成功，仍须分别读 Chat／Codex 的状态。
